# Trumen Guard: collision warning on any phone

**WIUT Hackathon 2026 final, Computer Vision track. Mode: Partner product for Toyota and BYD Royal Motors after-sales.**

Live: **https://trumen-com.github.io/road-vision/** (open it on a phone, tap *Use my camera*, or try a sample crash clip).

A phone mounted on the windscreen watches the road and warns the driver, out loud, about a car ahead or a pedestrian,
cyclist or motorcyclist moving into the path, before contact. Everything runs inside the phone's browser: no video
leaves the phone, there is no server cost per car, and nothing needs to be installed.

## Run it

```bash
cd guard
ONNXRUNTIME_NODE_INSTALL_CUDA=skip npm ci   # Node 20+; the env var skips a CUDA download for the offline evaluation
npx vite app                      # dev server: http://localhost:5173
npx vite build app --outDir ../dist --emptyOutDir   # static site in guard/dist (deploy anywhere)
```

The site deploys to GitHub Pages from this repository on every push (`.github/workflows/pages.yml`), so the
deployment history is in the Actions tab.

### Tests

```bash
npx tsx --test test/engine.test.ts     # physics checks: time to contact, tau-dot, metric offset, crossing pedestrian
```

### Reproduce the test results

```bash
# 1. data: Nexar Collision Prediction Dataset, public test split (667 clips, 2.9 GB) -> ../guard_data/nexar
bash eval/download_nexar.sh test-public

# 2. detector over every clip at 10 fps (same Detector class as the browser, onnxruntime-node), cached as JSON
npx tsx eval/extract_dets.ts --list ../guard_data/test_public.txt --out ../guard_data/dets_test

# 3. training windows from the TRAIN split, the risk model, and its export for the browser
bash eval/train_pipeline.sh 150
npx tsx eval/score.ts --dets ../guard_data/dets_train --out /tmp/t.csv --features results/train_agg.jsonl --agg 1 --no-model 1
(cd eval && python3 train_model.py --features ../results/train_agg.jsonl --data ../../guard_data/nexar --split train --out ../app/public/models/risk_model.json)

# 4. replay the engine over the test clips and compute the metrics shown on the site
npx tsx eval/score.ts --dets ../guard_data/dets_test --model app/public/models/risk_model.json --out results/test_scores.csv --timeline results/test_timeline.json
python3 eval/report.py --scores results/test_scores.csv --timeline results/test_timeline.json --data ../guard_data/nexar --out app/public/results/results.json
```

The optional visual model is trained with `train/visual_risk.py` (CPU) or `train/train_visual_risk_colab.ipynb` (Colab T4).
We trained it on CPU on 600 training videos and checked it with `eval/visual_ablation.py`: alone it scored mAP 0.62 and,
averaged 50/50 with the geometric score, 0.66, below the 0.69 without it. **So the deployed app does not use it.** The app
would load `visual_backbone.onnx` and `visual_head.onnx` from `app/public/models/` if they were present.

## Results on the test set (Nexar public test split, 667 clips, never used for fitting)

| Version | mAP (Nexar protocol) | ROC AUC |
|---|---|---|
| Naive: biggest object in front, no tracking | 0.70 | 0.74 |
| Tracking + time to contact + path test, hand-set weights | 0.65 | 0.67 |
| **Trumen Guard** (learned trees over 2 s of features) | **0.69** (95% CI 0.64–0.76) | **0.72** |

On ranking, Trumen Guard ties the naive baseline. As a live warning (smoothing, hysteresis, one alarm per danger) it warns
before more crashes at the same false-warning rate: about 19% vs 15% at 60 false warnings per hour of normal driving,
36% vs 29% at 100, 51% vs 34% at 150. The shipping threshold was chosen on the training split (out-of-fold) before
testing: on the test split it warns before 21% of crash clips at 63 false warnings per hour. That false-warning rate is
too high for production; tuning on local roads is the first job of the pilot. Night/rain/road-type breakdown and the full
trade-off curve are on the site's *Test results* page; everything is regenerated by `eval/run_all.sh`.

A recorded run of the demo (four test clips with the overlay drawn from the engine's states) is in `demo/backup.mp4`.

## How it works

```
phone camera ─► YOLO11n (512×288, ONNX) ─► tracker ─► time to contact + path test ─► features (2 s) ─► risk model ─► warning
                                                     (looming fit, width-scaled offset)  (gradient-boosted trees)
                (optional, not deployed: frames at 4 fps ─► MobileNetV3 ─► temporal head ─► averaged with the risk)
```

* **Time to contact from one camera.** For an object approaching at constant speed, its image height *h* satisfies
  d(ln *h*)/dt = 1/TTC. We fit ln *h* against time over the last 0.8 s (up to 1.6 s at low frame rates) with a median of
  pairwise slopes (robust to one jumpy box), and subtract the half-window lag so the estimate is for now, not 0.4 s ago.
  Height, not width: a car that turns shows its side and gets wider, but not taller. `test/engine.test.ts` checks this
  against synthetic approaching cars with known time to contact.
* **Path test in metres.** Sideways offset from our path divided by the object's own width is constant with distance,
  so with a typical width per class (car 1.8 m, person 0.5 m, …) we get the offset in metres, and its slope over time
  is the sideways speed in m/s. An object is a threat if it is within half our width plus half its width of our path
  now, or will be at the time of contact (cut-ins, pedestrians stepping out). Our own turning is removed by
  subtracting the scene-wide sideways motion.
* **Risk model.** 16 frame features (shortest time to contact in the path, looming rate, size and closeness of the
  nearest object in the path, vulnerable road users, turning, …) are aggregated over the last 2 s (last, max, min,
  mean, change) and fed to gradient-boosted trees trained on the Nexar **training** split. The trees are exported to JSON
  and evaluated by the same 20-line walker in the browser and in the evaluation (parity checked to 1e-6). A fixed monotonic remap puts the alert thresholds at round numbers.
* **Visual risk (tried, not deployed: it lowered mAP).** A frozen MobileNetV3-Large embeds frames at 4 fps; a small temporal network trained on the
  Nexar training videos scores the last 2 s. It is averaged with the geometric risk (equal weights, fixed in advance).
* **Alerts.** Caution when the smoothed risk stays above 0.5 for two frames, brake above 0.75; it reacts within a
  frame and releases over 0.6 s so one danger gives one alarm. Silent below 8 km/h (phone GPS).

## Where inference runs, speed and cost

| | |
|---|---|
| Inference | On the phone, in the browser (onnxruntime-web: WebGPU if available, else multi-threaded WebAssembly) |
| Speed | The live frame rate is shown on the Drive page. Detector: 41–47 ms per frame on 2 CPU threads (Node.js, our test machine) |
| Cost per car | No server inference. Static hosting (GitHub Pages / CDN): under one cent per active car per month |
| Night, rain | Reported separately on the Test results page (Nexar labels light and weather per clip) |
| Local vehicles and plates | The detector's classes (car, bus, truck, motorcycle, bicycle, person, animals) cover the local fleet; plates are not read |

## Add-on: Trumen Scan (3D parts from a phone walk-around)

`scan/` turns a walk-around video or photos of a car into a 3D model of that car's exterior, split into 32 named parts
with sizes and search links, exported as glTF and JSON for other apps. Live at `/scan/` on the site; details,
models and licences in [scan/README.md](scan/README.md). Built during the final (10 October 2026) as a next product
for Royal Motors after-sales (handover condition record, trade-in, parts lookup).

## What was built during the final, and what was reused

Built during the final (10–11 October 2026): everything in `guard/`: the browser engine (tracker, time-to-contact fit,
metric path test, features, risk model, visual model integration, alerts), the evaluation harness, the training scripts and
notebook, the web app and the business case. Reused and declared: our elimination-round idea of a causal time-to-collision
risk score (`src/traffic/risk.py` in this repository), re-implemented for a moving camera; public libraries and weights listed above.
